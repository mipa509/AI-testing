Task Design

The benchmark trap was subtle on purpose

Models had to produce an ordered Markdown-plus-Python notebook draft for preliminary sizing of a square pad footing under service loads only. The task required assumptions, equations, code cells, a search over candidate sizes, a results table, and a final engineering conclusion.

Correct engineering outcome

  • Selected footing: 3.0 m x 3.0 m
  • Governing selection case: LC2
  • Reason: 2.9 m still fails no-uplift

What separated the models

  • Handling of qmin >= 0, not just qmax
  • Clear derivation from axial stress plus biaxial bending
  • Correct distinction between largest compression and governing selection
Important distinction: LC3 has the largest qmax at the selected size, but LC2 governs footing selection because it controls the no-uplift limit.

Main Findings

What strong models did differently

Signals of high-quality outputs

  • Explicit rigid-footing linear-pressure model
  • Derivation from q = N/A +/- Mx*y/Ix +/- My*x/Iy
  • Clear candidate-size search with pass/fail logic
  • Direct explanation of why 2.9 m fails
  • Correct separation of compression-governing and selection-governing cases

Repeated failure modes

  • Calling LC3 the governing case because it had the largest qmax
  • Weak or missing explanation of the no-uplift trap
  • Shortcut formulas with limited sign-convention grounding
  • Placeholder leakage or notebook export artifacts
  • Slow response times on otherwise strong drafts
The benchmark proved that a model can be numerically competent and still lose on engineering judgement if it frames the governing case incorrectly in the final conclusion.
Recommendations

How to use the v3 result set

Immediate decisions

  • Use gpt5.4-xhigh as the notebook-quality reference baseline.
  • Keep glm-5.1:cloud and minimax-m2.7-cloud as strong alternates.
  • Treat fast models as revision-friendly assistants, but still check governing-case wording.

Next benchmark improvements

  • Add more notebook tasks so the ranking is not driven by one trap.
  • Separate "largest demand case" from "governing selection case" in scoring sheets.
  • Normalize latency capture if practicality remains a tracked metric.
